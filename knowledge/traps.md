## WSL·셸

- **/tmp 는 Bash 호출 사이에 증발** (WSL VM 유휴 종료) — 호출을 넘겨 쓸 파일은 ~/ 나 /mnt/c.
- **인라인 셸 변수·루프 변수(`$i`, `$f`)는 도구 경유 호출에서 증발** — 명령은 반드시
  **스크립트 파일로 저장 후** `wsl -e bash <파일>` 로. 히어독·유니코드·백슬래시도 동일.
- **PowerShell 을 거친 히어독은 소리 없이 빈 결과**를 낳기도 한다 — 위와 같은 처방.
- **NGPC 롬셋 7z 는 WSL tar 로 못 연다** — Windows `tar.exe`(bsdtar)로 풀 것.
- **파이썬 `"a" + "b %s" % x` 는 마지막 조각만 포맷된다** (% 가 + 보다 우선) —
  긴 문자열 연결에 % 포맷을 섞으면 조각별로 괄호를 쳐라.

- **★ `ss2-sp-core/build.sh` 는 커밋 안 된 `build/` 편집을 조용히 버린다 — 그리고 재생성기는 "OK" 라고 찍는다.**
  `build/` 는 **독립 git 레포가 아니라** ss2-sp-core 에 속한 디렉터리다. 그래서 build.sh 의
  `git -C build reset --hard <upstream커밋>` 은 그 커밋이 상위 레포에 없어 **실패하고**,
  `|| git -C build checkout -- .` 로 넘어가 **build/ 를 상위 레포 HEAD 로 되돌린다.**
  이어지는 `git apply --3way src/ss2sp.patch` 는 이미 패치된 파일에 걸려 **no-op** 이 되므로,
  패치 파일에는 내 수정이 들어 있는데 **빌드된 .so 에는 안 들어간다.**
  `regen_patch.sh` 는 왕복 검증까지 통과해 「ss2sp.patch 갱신 OK」를 찍기 때문에
  **성공한 줄 알고 넘어가게 된다.** (실제로 그렇게 한 번 속았다 — 빌드 로그도 정상이었다.)
  → **`build/` 를 고쳤으면 `build.sh` 를 돌리기 전에 커밋해라.** 순서가 규칙이다:
  `build/ 편집 → regen_patch.sh → **커밋** → build.sh`.
  빌드 뒤 `grep <내가 넣은 심볼> build/libretro.c` 로 살아남았는지 한 번 확인하면 확실하다.

- **작업트리를 여러 방이 동시에 쓰면 남의 커밋에 내 변경이 딸려 간다.**
  같은 기계의 같은 체크아웃에서 두 방이 일하면, 한쪽의 `git add`/`git commit` 이
  **다른 쪽의 미커밋 변경을 함께 커밋한다.** 실제로 한 방의 `build/libretro.c` 수정이
  다른 방의 「오버레이 메뉴 롬별 분리」 커밋에 통째로 들어갔다(내용은 맞았으니 사고로 끝났을 뿐).
  → 남의 레포 디렉터리를 건드렸으면 **곧바로 커밋하고, 무엇을 왜 만졌는지 그 방에 알려라.**
  커밋 전 `git status --short` 로 **내가 안 만진 파일이 섞여 있는지** 먼저 봐라.

- **★ 시드(초기 문서 생성) 스크립트를 두 번 돌리면 그 사이 기여가 조용히 사라진다 — 그리고 「강제 푸시」로 오진하게 된다.**
  이 저장소에서 실제로 났다. `knowledge/traps.md` 가 **시드 커밋으로 두 번** 만들어졌다:
  `a9d4fe5`(1차, 3,450B) → `c77c1e9`(다른 방이 「롬 한글화」 절 추가, 7,286B) →
  … → **`29e89a7`(2차 시드, 다시 3,450B)** → 그 뒤 커밋들이 그 위에 쌓였다.
  즉 2차 시드가 파일을 통째로 덮어써 c77c1e9 의 기여가 없어졌다.
  * **커밋은 하나도 안 없어졌다.** `c77c1e9` 는 지금도 main 의 조상이다
    (`compare/c77c1e9...main` → `behind_by 0`, 부모 사슬 14번째).
    **없어진 것은 파일 내용뿐**이다.
  * 그래서 오진이 쉽다 — 「내 절이 없다 + 이력에서 안 보인다」를 보고 force-push 를 의심하게 된다.
    이력에서 안 보인 것은 **API 로 커밋을 12개만 받아서**였다. 그 커밋은 14번째에 있었다.
  * 뒤에 온 사람은 **덮인 판 위에 이어서 쓰게 된다.** 실제로 그랬다(3,450B 에서 이어 붙였다).
  → **시드 스크립트는 파일이 이미 있으면 건너뛰게 만들어라.** 덮어쓰기가 기본이면 안 된다.
  → 원인 진단은 이력 목록의 길이로 하지 말고 **도달 가능성**으로 해라:
  `compare/<sha>...main` 의 `behind_by 0` 이면 그 커밋은 조상이다. 목록은 페이지에서 잘린다.
  → 내용이 언제 사라졌는지는 **커밋별로 파일을 받아 크기를 훑으면** 한눈에 보인다
  (`contents/<path>?ref=<sha>`). 같은 크기로 되돌아간 지점이 범인이다.

## 측정기가 고장난 채로 재고 있는 경우 (에뮬 하네스)

전부 「다르다/같다」를 보고하기 **전에** 측정기부터 재서 찾은 것들이다.
공통 규칙 하나: **같은 조건을 두 번 돌려 재현되는지 먼저 보라.**
재현이 안 되면 그 차이는 내 변경의 증거가 아니다.

- **★ 코어가 호스트 시각을 읽는다 — 램 diff 가 매번 흔들린다.**
  `mednafen/ngp/rtc.c` 의 `time()`/`localtime()` 때문에 **같은 `.so` 로 같은 대본을
  두 번 돌려도** 램이 달라진다. 실측: SvC 9바이트, SS2 3바이트.
  코어 두 벌을 비교하다가 「SVC·SS2 가 회귀했다」고 결론 낼 뻔했다 —
  **내 변경이 그 게임에서 아예 안 불리는 코드였는데도** 그랬다.
  → 비교 전에 **각 코어를 두 번 돌려 불안정 바이트를 실측으로 빼고**, 양쪽에서
    안정한 바이트만 비교하라. 불안정 바이트가 많으면 「판정불가」로 내라 — 「같음」이 아니다.
  → 램 diff 로 주소를 사냥하는 모든 작업(이력 링·홀드 카운터·act)이 이 잡음 위에 있다.
    「같은 상태 두 번 덤프로 흔들리는 바이트 제외」가 그래서 첫 단계다.
  → 따름정리(이식소, M2 회귀 도구 부검): **잡음은 비교와 같은 시간 간격으로 재야 한다.**
  기준 2회(a,b)→새것 2회(c,d) 순서로 돌리면 잡음은 인접 실행(a↔b)에서 재는데 비교는
  두 칸 건넌 실행(a↔c)끼리 하게 된다 — 코어가 호스트 시각을 읽으면 그 간격 차가 곧
  거짓 「다름」이다 (같은 코어 둘을 넣어도 204/2738 차이가 났다). 엇갈려 돌려라:
  a(기준) b(새것) c(기준) d(새것) — 잡음은 a↔c·b↔d, 비교는 a↔b, 같은 간격을 건넌다.
  그리고 「판정불가」는 FAIL 이 아니라 「모른다」로 따로 분류하라.

- **★ 게임마다 「결정적인 창」이 있다 — 그 밖에서 비교하면 아무 뜻이 없다.**
  SS2 는 콜드 부팅 후 **약 1,200프레임까지만** 재현된다. 그 뒤로는 같은 코어끼리도
  화면이 **24,000바이트** 넘게 갈린다(어트랙트/RNG로 보인다).
  같은 대본에서 SvC·메탈슬러그·아랑전설·KOF R-2 는 끝까지 재현됐다 — **게임마다 다르다.**
  → 회귀 대본은 그 창 안에서 끝내라. 창의 길이는 **재 보고** 정해라, 짐작하지 말고.

- **★ 하네스 기본값이 코어의 분기 블록을 통째로 꺼 놓을 수 있다.**
  `ngprun` 의 기본값은 `ngp_ss2sp=disabled` 인데, 코어의 입력 매크로·폴드가 전부
  `if (ss2sp_enable)` 안에 있다. 그래서 그 상태로 「두 코어 출력이 같다」를 재면
  **입력 분기를 한 줄도 안 지나간 채** 같게 나온다 — 「같다」와 「아무것도 안 쟀다」가 구별이 안 된다.
  → 검사가 **실제로 그 코드를 지나가는지** 먼저 확인하라. `NGP_OPTS="키=값,…"` 로 켠다.
  → 일반화: **켜야 도는 기능을 끈 채로 무회귀를 선언하지 마라.** 회귀 스크립트가
    옵션을 명시하지 않고 코어 초기값에 기대고 있다면 그것도 같은 함정 자리다.
  → 본부 실사고(2026-09-04): `svcrun` 으로 SvC 엔진을 재던 env 가 `ngp_ss2sp=disabled` 였다.
    SvC 의 `svcsp_frame()` 호출도 같은 `if (ss2sp_enable)` 안이라 **즉발 강키·착지 선입력·SP 트리거가
    통째로 안 돌았고**, 「R1/X/Y 무반응」이 며칠 미해결로 남았다. SvC 실측 env 는
    `ngp_ss2sp=enabled ngp_svcsp_engine=enabled`. 살아있는지 확인: `SVCSP_DEBUG=1` + 지상 B 한 번 →
    `[land] g-edge …` 줄. 롬 게이트는 `SVCSP_ROMTHR=2 SVCSP_DEBUG=1` → `[svcsp] rom 문턱` 줄.
    덤으로 svcrun 대본의 `!w` 는 **라벨 없으면 무시**된다 — 프로브 CSV 가 헤더만 남으면 이걸 의심.

## 안드로이드

- **sdcard 는 noexec — dlopen 이 안 되는 기기가 많다.** 내려받은 코어(.so)는 앱 내부
  저장소(getFilesDir)에 두고 로드할 것.
- **AAudio 는 에러 콜백 없이는 장치를 뺏기면 무음으로 죽는다** — setErrorCallback +
  재생성, onPause 에서 스트림 반납이 정석.
- **큰 파일(수백 MB 팩)을 ByteArrayOutputStream 으로 받으면 OOM** — 스트리밍으로 파일에.
- **다운로드 파일은 매직 검사** (IPS=`PATCH`, ELF=`7f 45 4c 46`) — 오류 페이지를
  패치/코어로 저장하는 사고 방지.
- 옆설치 서명은 고정 키스토어(잃어버리면 유저 전원 재설치) — 키 이름·자리는 SP 방 관리.

## 롬 한글화 (그래픽·글리프)

  칸만 배정한다. 모자라면 **거부**하고 낱말을 줄여라 (「나가기」→「종료」).

  확인하고, 잰 폭을 빌더에 한계로 박아 넘치면 거부.
- **같은 낱말 타일이 롬에 여러 벌 있다.** 메탈슬러그 1st 게임오버의 `RETRY` 2벌,

  「32타일 폭 띠」로 보였고 어떤 정렬로 그려도 글자가 겹쳤다. VRAM 한 장으로
  「한 글자 = 연속 4타일(좌상·우상·좌하·우하)」이 바로 나왔다. 1st 의 페이지 주소도
  같은 방법으로 풀었다. **화면 → char RAM → 롬 역추적**이 제일 빠른 길이다.
- **값을 몰라도 «차이»로 롬을 찾을 수 있다.** 메탈슬러그 2nd 대사 코드열을 찾을 때,
  화면에서 읽은 글자 순서를 **인덱스 차이**로 바꿔 훑었다. 기준값을 몰라도 차이는
  기준과 무관해서 4MB 에서 한 곳만 걸렸고, 덤으로 글리프 표 기준까지 확정됐다.
- **훑기 끝점을 한 종류로 못 박지 마라.** 코드열 끝 제어코드가 뭉치마다 다르다.
  한 종류로 박으면 뭉치를 놓치고, 마지막 제어코드까지 무조건 끌고 가면 표 앞부분을
  코드로 잘못 읽어 또 놓친다. 제어코드 자리를 **전부 후보로 놓고 조건을 통과하는
  가장 긴 것**을 고를 것. 후보마다 다시 훑으면 O(n²) 라 4MB 에서 안 끝난다 —
  앞에서 한 번만 훑으며 판정하면 O(n) (10분 초과 → 0.4초).
- **훑는 도구의 시작 홀짝을 고정하지 마라.** 메탈슬러그 2nd 의 대사 뭉치를 찾는
  훑기를 `i = 0` 에서 `i += 2` 로 짰더니 **짝수 주소만** 봤다. 마침 짝수였던 두 뭉치는
  걸리고 홀수였던 두 뭉치는 통째로 안 보였는데, 그걸 모르고 「롬 전체에 두 뭉치뿐」
  이라는 **결론까지 냈다**. 도구의 빈틈을 데이터의 성질로 읽는 게 이 사고의 본질이다.
  u16 을 훑으면 홀짝 둘 다 돌려라. 「전부 찾았다」는 도구가 못 볼 자리를 따진 뒤에.
- **같은 글리프가 표 여러 곳에 있으면 표마다 다 계산해 보라.** 메탈슬러그 2nd 는
  같은 글자 그림이 표 세 곳에 있다. 화면에서 뜬 글리프의 롬 주소를 «어느 표» 기준으로
  인덱스로 바꾸느냐에 따라 값이 완전히 달라진다. 한 표 기준으로 못 찾았다고
  「인덱스 방식이 아니다」로 넘어갈 뻔했다 — 실제로는 옆 표 기준이 맞았다.
- **8×8 칸에 획 많은 한글은 뭉갠다.** 7×7 글꼴에서 연↔련은 64픽셀 중 12픽셀,
  자↔짜는 17픽셀 차이다. 검수자가 오독한 전력이 있다. 8×8 자리에는 **획이 단순한
  낱말**을 골라라 (「종료」→「끝내기」, 「재시도」→「다시하기」).

  메탈슬러그 2nd 한패를 넉 판 내고서 유저 제보를 받았다 — 「메뉴랑 체력은 한글인데
  미션 설명은 전부 영어로 나온다」. 재현됐다. **NGPC 는 게임 안에 언어 항목이 없고
  본체(BIOS) 언어 설정을 게임이 읽는다**(RAM `0x6F87`, 0=일본어 1=영어). 그 게임은
  그 값에 따라 **일본어판 글과 영어판 글을 아예 따로** 쓴다. 한패는 일본어 쪽을
  옮긴 것이라, 본체가 영어면 원문 영어가 그대로 나온다.
  * 왜 못 잡았나 — 내 하네스가 코어 옵션 `ngp_language` 기본값을 `japanese` 로
    먹이고 있었다. 화면 순회를 몇 번을 돌려도 **늘 같은 값**이었다. 위의 소리 사고와
    달리 **화면 검증이 고장난 게 아니다** — 화면은 정확히 옳았고, 다만 **경우의 절반을
    한 번도 안 그렸다.** 「전부 통과」가 「전부 봤다」가 아니었다.
  * 처방 ①: 하네스가 **고정해 놓은 값들을 목록으로 적어 두고**, 릴리즈 전에 한 번은
    **반대 값으로도** 돌려라. 기본값은 편의지 사실이 아니다.
  * 처방 ②: 그런 축이 있으면 **패치가 축을 없애 버리는 쪽**이 낫다. 유저에게
    「설정을 바꾸세요」라고 안내하는 건 마지막 수단이다 — 안 읽는다.
    메탈은 언어를 보는 자리 25곳의 비교 opcode를 한 바이트씩 바꿨다:

        C1 87 6F 3F 00   CP  (0x6F87),0     ← 일본어인가?
        C1 87 6F 3C 00   AND (0x6F87),0     ← 0 을 써 넣으면서 Z 를 세운다

    값이 0 일 때 CP 와 AND 는 Z·S·C 가 같고, AND 는 **그 자리를 0 으로 만들어서**
    한 번 지나가면 그 뒤로 계속 일본어다. 뒤따르는 분기가 자리마다 다르므로
    (JR Z·JR NZ·JRL NZ·JP NZ·RET Z) **전부 Z/NZ 만 쓰는지 세어서 확인**하고 바꿔라 —
    넘침·패리티를 보는 자리가 하나라도 있으면 AND 로는 안 된다.
  * 같은 수가 KOF R-2 에도 통한다. 다만 거기는 그 자리가 **`0x00011C` 한 곳뿐**이라
    「부팅 때 반드시 지나는가」를 따로 확인해야 했다. 역어셈해 보니 리셋 직후
    초기화 구간이고, 게임은 결과를 제 변수(`0x400A`)에 **한 번만 캐시**한다 —
    한 바이트로 끝난다. **검사 자리가 하나뿐일 때는 「그 길을 반드시 지나는가」를
    코드로 확인하라.** 여러 곳이면 아무 데나 걸리지만 한 곳이면 안 걸릴 수 있다.
  * **★ 그런데 위의 「AND 로 바꿔라」가 틀렸다 — 처방 자체에 부작용을 심었다.**
    나는 `CP`(읽기 전용)를 `AND`(읽기-수정-쓰기)로 바꿔 놓고, 「그 자리가 0 이
    되니 한 번만 지나가면 끝」이라며 **되쓰기를 이점으로 릴리즈 본문에 적기까지
    했다.** `0x6F87` 은 **본체(BIOS) 사용자 설정 램**이다. 에뮬은 세션 램이라
    아무 표도 안 나지만, 실기에서 그 영역이 배터리 백업이면 **유저 본체의 언어
    설정이 실제로 바뀐다.** 되돌리기도 어렵다. 화면 54장 픽셀 대조를 통과했는데도
    못 잡았다 — **화면으로는 영영 안 보이는 종류**다. (이식소가 R-2 에 같은 수를
    검증하다 잡아 줬다. 판번호를 올려 교체했다.)
    * 무엇을 안 봤나 — 명령을 고를 때 **「플래그가 같은가」만 보고
      「메모리를 건드리는가」를 안 봤다.** 읽기 전용 명령을 읽기-수정-쓰기로
      바꾸는 짓은, 그 대상이 **게임 밖(본체 설정·세이브·시계)** 이면
      화면에 안 나타나는 부작용이다.
    * 바른 처방 — **비교는 건드리지 말고 분기만 고정하라.** 조건코드만 바꾸면
      메모리에 한 바이트도 안 쓴다 (TLCS-900 은 0=F 절대아님, 8=T 늘):

          JR  Z  (66) → JR  T (68)     JR  NZ (6E) → JR  F (60)
          JRL NZ (7E) → JRL F (70)     JP  NZ (DE) → JP  F (D0)
          RET Z  (B0 F6) → RET T (B0 F8)

    * 확인은 **「안 썼다」를 직접 재라** — 롬 전체에서 그 주소를 **목적지로 삼는**
      명령이 0곳인지 전수 검사하고, 빌드 검사에 상수로 박아라.
      「화면이 같다」는 이 축의 증거가 **아니다.**

- **★ 새 도구를 넘길 때는 «자가 반응하는지»를 도구가 스스로 재게 하라 —
  안 그러면 자를 쥔 손이 고장나도 「통과」가 나온다.**
  위의 언어 축 대조 도구(`ngp_langdiff.py`)를 만들어 옆방에 넘겼더니 바로 걸렸다.
  받은 쪽이 `~/ngprun` 으로 돌렸는데 그 빌드가 **`NGP_LANG` 을 안 읽는 옛 것**이라
  두 판이 당연히 같았고, 「다름 0 = 통과」로 읽힐 뻔했다. 같은 기계에 같은 이름의
  하네스가 여러 벌 있었던 것이다(맞는 것은 `m0/ngprun_all` 이었다).
  * 왜 고약한가 — **「게임이 그 축을 안 본다」와 「도구가 축을 안 넘긴다」가
    똑같이 «다름 0»으로 나온다.** 결과만 봐서는 구분이 안 된다.
  * 처방 ①(약함): 「먼저 안 고친 롬으로 돌려 다름>0 이 나오는지 보라」는 대조군.
  * 처방 ②(셈): **바뀌어야 할 그 값을 에뮬레이터 상태에서 직접 읽어라.**
    언어 축이면 램 덤프에서 언어 바이트를 꺼내 **일본어 판 0 · 영어 판 1** 인지
    보고, 아니면 **결과를 아예 내지 않는다.**

        램 덤프 오프셋 0x2F87  (= NGP RAM 0x6F87 − 0x4000)
        0/1 이 아니면 → "하네스가 NGP_LANG 을 안 넘긴다. 이 판정은 가짜다"

    도구가 제 자를 스스로 재게 하는 쪽이 사람이 대조군을 잊지 않기를 바라는 것보다 세다.
  * 일반형: **도구가 「내가 바꾼 조건이 실제로 바뀌었나」를 먼저 확인하고,
    아니면 침묵하라.** 결과를 내는 것보다 안 내는 것이 나은 경우가 있다.

- **★ 「원본」이라고 부르는 그 롬이 원본인지 해시로 확인하라.**
  여덟 게임을 언어 축으로 훑을 때 `~/thumbroms` 를 원본으로 썼는데
  **넷이 순정이 아니었다** — `lb` 는 아예 옛 한패본(LastBlade_Korean_v1.2)이었고,
  `svc` 는 한패 0.172 본이었다. 그 위에 최신 IPS 를 덧씌워 놓고 「순정 대비」라고
  적었다. 결론은 우연히 맞았지만 **방법이 틀렸고, 맞은 줄도 몰랐다.**
  * 이건 methodology 에 이미 「검증은 반드시 깨끗한 원본으로 — 작업 폴더의 롬은
    이미 패치본인 경우가 많다」고 적혀 있던 함정이다. **적어 놓고 밟았다.**
  * 처방: 릴리즈 본문의 **원본 해시**로 정체를 먼저 확인하라. 이름이 `orig.ngc`
    라고 순정이 아니다 — 한 방에 `orig` 와 `base` 와 `orig_good` 이 같이 있고
    그중 하나만 순정인 경우가 실제로 있었다.
  * 훑기 도구를 쓸 때는 **원본 crc32 를 결과에 같이 찍어라.** 그러면 나중에
    「무엇을 잰 것인지」가 기록에 남는다.

## 안드로이드: 풀스크린 액티비티 위의 Dialog 가 패드 키를 못 받는다 (본부, 2026-09-04)

PocketCore 런처(Theme.NoTitleBar.Fullscreen + immersive) 위에 `new Dialog(a)` 로 띄운 실행 전 선택창이
에뮬에서 **윈도우 포커스를 못 받았다**(dumpsys window mCurrentFocus 가 계속 MainActivity). 터치는 되는데
DPAD/버튼은 액티비티의 dispatchKeyEvent 로 간다 → 「확인을 눌렀는데 창이 또 열린다」.
- 해결: 액티비티가 열려 있는 창(curSheet.isShowing())을 알고 키를 `sheet.handleKey(e)` 로 넘긴다. 창이 포커스를
  받은 환경에선 Dialog 의 OnKeyListener 가 같은 함수를 부르므로 이중 처리는 없다(창 둘 중 하나만 키를 받는다).
- 확인법: `adb shell dumpsys window | grep mCurrentFocus` 를 키 보내기 전후로.

## 패드 버튼 의미는 KeyMap 기능으로만 — 날 KEYCODE_BUTTON_A/B 폴백을 두지 마라 (본부, 2026-09-04)

KeyMap 기본표는 기능 `b`(펀치 자리=확인) → KEYCODE_BUTTON_B, 기능 `a`(킥 자리=취소) → KEYCODE_BUTTON_A. 그리고
`KeyMap.isGamepad()` 는 BUTTON_* 코드면 **출처 무관** true 라 기능이 항상 계산된다. 여기에 「BUTTON_A=확인, BUTTON_B=취소」
같은 날 코드 폴백을 얹으면 같은 버튼이 확인·취소 둘 다 참이 되어 if 순서로 결정된다(실측: 킥 버튼이 취소 대신 토글·시작).
- 규칙: 기능이 있으면 기능만. 날 폴백은 기능이 없는 DPAD·ENTER·BACK·START 만. 배정 없는 패드 버튼은 삼킨다
  (안 삼키면 시스템 폴백이 Y 를 BACK 으로 바꿔 앱이 꺼진다).
- 에뮬 `adb shell input keyevent KEYCODE_BUTTON_B` = 확인, `KEYCODE_BUTTON_A` = 취소 로 검증.

## 해시표 없이 순정 롬을 가리는 자 — IPS 가 쓰는 바이트 대비 «실제로 바뀐» 바이트 (1-f7, 2026-09-04)

위 「★ 「원본」이라고 부르는 그 롬이 원본인지 해시로 확인하라」의 짝이다.
그 절의 처방은 **해시를 미리 알고 있을 때** 쓴다. 모를 때 쓸 자가 하나 더 있다.

**IPS 를 입혀 보고, 「IPS 가 쓰는 총 바이트」와 「실제로 값이 바뀐 바이트」를 대 본다.**

    순정이면        70~90%   (겹쳐 쓰는 값이 우연히 같은 자리만 빠진다)
    이미 패치본이면  1% 미만  (IPS 가 쓰려는 값이 이미 거기 있다)

실측 (2026-09-04, 같은 자로 여덟 게임):

    SvC   rom/base.ngc            81.4%  순정
    R-2   rom/kofr2.ngc           74.4%  순정
    SS2   rom/ss2.ngc              0.3%  ★ 이미 패치본
    SS2   work_lang/ss2.pristine.ngc  85.7%  순정
    SS1 86.4% · 월화 93.5% · 아랑 82.0% · 메탈1 79.0% · 메탈2 74.2%  전부 순정

`rom/ss2.ngc` 는 **이름도 위치도 원본 자리**였고 본부가 대조군으로 쓰고 있었다.
143,111바이트를 쓰는 IPS 를 입혔는데 **359바이트만 바뀌었다** — 구버전 한패본이었다.
그 롬을 원본으로 삼은 언어 축 판정은 그 자리에서 무효였다.
(나중에 유저가 준 순정 묶음과 대 보니 `ss2.pristine.ngc` 가 `[!]` 덤프와 crc 까지 같았다.)

코드는 세 줄이면 된다 — IPS 레코드를 풀면서 겹쳐 쓰기 전에 세면 그만이다:

    changed += sum(1 for k in range(rl) if b[off + k] != new[k])
    tot     += rl
    # 끝나고:  changed / tot  ·  0.3 미만이면 순정이 아니다

**한계 — 이걸 해시 대신 쓰지 마라.**
- 이 자가 재는 것은 「이 롬이 **이 패치(의 어떤 판)를 이미 지고 있는가**」다.
  「이 롬이 어느 덤프인가」가 아니다. `[!]` 와 `[a1]` 을 못 가른다 — 그건 해시 몫이다.
- 그래도 실제로 밟는 사고는 대부분 앞쪽이다. 여덟 게임 훑을 때 넷이 오염이었던 것도,
  본부 대조군이 무효였던 것도 전부 「구버전 패치본을 원본이라 불렀다」였다.
- 비율이 100% 가 되는 일은 없다. IPS 가 쓰는 값이 순정에도 우연히 같은 자리가 늘 있다.
  70~90% 가 정상이고, **10~50% 같은 어중간한 값이 나오면 그건 부분 패치본**이니
  그때는 손을 멈추고 해시로 가라.

같이 볼 것: `methodology.md` 「검증은 반드시 깨끗한 원본으로」 · 위 ★ 절.

## 글 끝을 0x00 으로 찾으면 «2바이트 코드» 한가운데서 잘린다

2바이트 글자 방식을 쓰는 롬에서 `find(b'\x00')` 은 틀린 도구다. 색인
0x100·0x200·… 은 **뒷바이트가 0x00** 이라 그 자리가 글 끝으로 읽힌다.
게임은 앞바이트를 만나면 다음 한 바이트를 값으로 집어삼키고 넘어가므로,
끝을 찾을 때도 **똑같이 걸어야** 한다.

    while rom[i]:
        i += 2 if 1 <= rom[i] <= 7 else 1

카드 파이터즈 2 에서 밟았다. 카드 이름 `ナコルル/⟪100⟫`(NAKORURU(C))가
`ナコルル/` 로 잘려 있었다.

**들키는 법이 중요하다.** 잘린 글은 잘린 채로도 말이 되는 수가 많아 눈으로는
안 걸린다. 고친 뒤 **세는 것이 변하는지**를 봐라 — 쓰는 한자가 391종에서
404종으로 늘었다. 그 13종이 잘린 뒤쪽에 숨어 있던 증거다.

## 「안 쓰는 자리」를 논증으로 닫지 마라 — 채워 넣고 재라

빈 자리를 찾을 때 바이트 무늬로 훑는 검사(그 구역을 가리키는 값이 있나,
어느 페이지 꼬리인가)는 **롬에 따라 포화된다.** 카드 파이터즈 2 는 2MB
안에서 「하위 바이트 0 인 카트 주소처럼 읽히는 3바이트」가 14,325곳
나와서, 페이지 검사가 롬의 97% 를 「쓰인다」로 칠했다. 어떤 크기의 자유
구역도 0곳 — 이건 답이 아니라 **신호가 없다**는 뜻이다.

논증이 포화되면 **측정**으로 간다.

    ① 후보 구역을 눈에 띄는 무늬로 채운 롬을 만든다
    ② 원본과 채운 롬에 같은 대본을 돌린다
    ③ VRAM 덤프·화면·시스템 RAM 을 통째로 대조한다

**반드시 먼저 검사가 반응하는지 증명한다.** 확실히 쓰는 자리(원본 글꼴표)를
일부러 뭉갠 롬으로 같은 대조를 해서 «달라지는 것»을 봐야 한다. 안 그러면
0 차이가 「안 읽는다」인지 「검사가 눈멀었다」인지 못 가른다. 실제로
카드 파이터즈 2 에서 후보 구역은 40개 중 0개, 일부러 뭉갠 롬은 8개가
달라졌다.

**그래도 «지나간 화면»만 덮는다.** 이건 검사의 흠이 아니라 범위의 문제이니,
결과를 적을 때 「안 읽는다」가 아니라 **「이 화면들에서는 안 읽었다」**로
적어야 한다. R-2 에서 6,000프레임 읽기 0회였던 자리를 코드 다섯 곳이
쓰고 있었다 — 안 가 본 화면이었을 뿐이다.

## 「반응하는가」만으로는 모자란다 — **「조용한가」도 재라**

차이를 신호로 읽으려면 대조가 두 쪽을 다 통과해야 한다.

    ① 반응하는가   확실히 쓰는 자리를 뭉갠 입력은 **달라야** 한다
                   (0 차이가 「같다」인지 「내 눈이 멀었다」인지 가른다)
    ② 조용한가     **같은 입력**을 두 번 넣은 것은 **같아야** 한다
                   (차이가 「진짜」인지 「잡음」인지 가른다)

②를 빠뜨리고 자리 10만 바이트를 버릴 뻔했다. 카드 파이터즈 2 에서 빈 구역을
채울 때마다 시스템 RAM 이 40바이트쯤 달라져서 「게임이 그 구역을 읽는다」로
읽었다. 구역 넷을 하나씩 갈라 봐도 **넷 다** 같은 정도로 달라졌다 — 그
「넷 다 걸린다」가 오히려 힌트였다.

**같은 롬을 두 번 돌려 보니 47바이트가 달랐다.** RAM 은 잡음 채널이었다.
VRAM 덤프 40개와 끝 화면은 두 번 돌려도 똑같았고, 뭉갠 롬에서는 달라졌다 —
그 둘만 쓸 수 있는 채널이었다. 그 둘로 보면 구역 넷은 **차이 0** 이었다.

도구가 채널을 스스로 고르게 하는 게 낫다(`cf2_arena.py`).

    쓸 수 있는 채널 = 잡음 대조에서 «0» 이고 반응 대조에서 «0이 아닌» 것
      잡음이면 버린다 · 반응이 없어도 버린다

**「여러 후보가 전부 걸린다」는 잡음의 냄새다.** 진짜 원인이라면 갈렸을
것이다. 그때는 원인을 더 찾지 말고 **아무것도 안 바꾼 대조**를 먼저 돌려라.

## 완성도는 «원본»으로 세라 — 만든 것을 세면 빠뜨린 건 0으로 보인다

카드 파이터즈 1 을 「완역」이라고 했다. 검수맨이 1,509항목을 전수로 읽고
**「미번역: 0」**이라고 했다. 그런데 화면을 켜 보니 용어집 목차가 영어였다.

세어 보니 **383개가 통째로 빠져 있었다.** 덱 만들기·앨범·저장·통신·전적 —
게임을 켜면 바로 보이는 자리들이다.

**검수맨은 성실했고 「미번역 0」도 참이었다.** 텍본을 **내 번역표에서**
만들었기 때문이다. 내가 안 뽑은 383개는 검수 대상에 **존재하지도 않았다.**
없는 것을 못 봤다고 할 수는 없다.

    내가 센 것    번역표 1,076개 중 미번역 0개      ← 참인 채로 틀렸다
    롬을 센 것    포인터 표의 글 슬롯 1,358개
                  그중 번역표에 있는 것 982개       ← 376개가 없다

**이건 「대충 봤다」와 다른 종류의 실패다.** 검사가 성실해도 0 이 나온다.
검사의 «대상 집합»을 검사받는 쪽이 정했기 때문이다.

### 규칙

**세는 기준은 언제나 원본이다.** 번역률·처리율·완성도를 말할 때, 분모는
내가 만든 목록이 아니라 **원본에서 센 수**여야 한다. 도구가 그렇게 세게
만들어라 — 「롬의 포인터 표를 훑어 글이 몇 개인가」를 도구가 매번 다시
세고, 내 표와 대조해 «없는 것»을 소리내게 하라.

카드 파이터즈 2 는 처음부터 원본 포인터 표를 훑어 작업 목록을 만들었다.
그래서 세어 보니 슬롯 2,640 = 작업 목록 2,640 으로 빈 곳이 0이었다.
**같은 사람이 같은 날 만든 두 도구가 갈렸다** — 구조가 갈랐지 사람이
갈린 게 아니다.

### ★ 두 번째 사례 — 다른 사람, 다른 게임, 같은 모양

같은 날 KOF R-2 쪽에서도 이 규칙을 돌려 봤더니 걸렸다.

    원본 스캔    4,049개
    내 번역표    2,652개
    표 밖        2,122개  →  그중 일문 85개

**캐릭터 프로필이 통째로 빠져 있었다** — 신장·체중·생일이 14명분 전부
원문 그대로다. 캐릭터를 고를 때 나오는 화면이다.

그리고 **예산 계산에 쓰던 「남은 일문 6줄」이 틀렸다.** 그 수를 내는 도구가
**자기 번역표**를 읽고 있었다. 표에 없는 85개는 애초에 안 세어진다.

**한 게임이면 그 게임 사정이지만, 두 게임에서 다른 사람이 같은 모양으로
밟았으면 방법의 문제다.** 도구를 각자 따로 만들었는데도 둘 다 「내가 만든
목록」을 분모로 삼았다. 그게 자연스러운 실수라는 뜻이다.

차이는 하나였다 — **한쪽은 배포 전에 잡혔고, 한쪽은 배포한 뒤에 잡혔다.**

### 딸린 규칙 둘 — 세는 도구도 의심하라

「표 밖 0개」가 나왔는데 알고 보니 스캔 API 를 잘못 부른 것이었다.
제대로 부르고 나서야 2,122 가 나왔다. **0 이 나오면 먼저 내 호출을
의심하라** — 반응 증명의 또 다른 얼굴이다. 세는 도구가 0 을 낼 때는,
일부러 하나를 빼고 돌려서 1 이 나오는지부터 봐라.

### 오늘 나온 셋이 한 뿌리다

    ① 반응하는지 증명하라   0이 「같다」인지 「내 눈이 멀었다」인지
    ② 조용한지 증명하라     차이가 「진짜」인지 「잡음」인지
    ③ 원본을 세라           「없는 것」이 0으로 보이는지

셋 다 **검사가 «무엇을 못 보는지»를 검사하지 않은 것**이다.

### 딸린 규칙 하나

**「미완이라고 적고 내자」는 못 쓴다.** 미완이라고 적으려면 무엇이 미완인지
알아야 하는데, 검증을 안 했으면 그걸 모른다. 실제로 이 건에서 나는
「화면 검증 미완」이라고 적을 참이었고, 진짜 문제는 **번역 미완**이었다.
**내가 모르는 것을 본문에 적을 수는 없다.**

## ④ 검사자가 포화되지 않았는지 증명하라 — 「걸렸다」는 신호가 아닐 수 있다

앞의 셋은 **검사가 아무것도 못 볼 때**를 다뤘다. 넷째는 반대다.
**검사가 무엇이든 다 걸어 버릴 때**, 「걸렸다」는 아무 뜻이 없다.

죽은 자리를 찾는 일에서 나왔다. 2MB 롬 안의 10KB 구역을 두고
「이 자리를 가리키는 코드가 있나」를 물었고, 있다고 나왔다.

    직접 포인터 훑기      SS2 445 · R-2 427 · SvC 1023 곳이 걸렸다

그럴듯했다. 그런데 **같은 크기·같은 덩이 분포로 「아무 자리」를 잡아** 같은 훑기를 돌렸다.

    SS2   실제  445   무작위 [979, 299, 427, 340]
    R-2   실제  427   무작위 [693, 394, 571, 430]
    SvC   실제 1023   무작위 [906, 1253, 2833, 780]

**실제 값이 무작위 범위 «안»이고, 셋 다 평균보다 낮았다.**
2MB 를 24비트로 훑으면 우연 일치가 신호를 통째로 덮는다.

    → 이 자는 결과가 «0» 일 때만 뜻이 있다. 0 이 아닌 숫자는 신호가 아니라 배경이다.

같은 날 자원 페이지 검사도 같은 병이 드러났다. 그 도구는 R-2 와 SvC 를
**「100% 쓰임, 남는 자리 0」**으로 판정했다. 롬이 100% 살아 있을 리 없다.
**난수 바이트**를 넣어 봤다 — 롬이 아니라 그냥 난수다.

    실제 롬   페이지 머리 12,018 개 · 92.7% 덮임
    난수 3회  페이지 머리   989~1,071 개 · 85.1% · 85.4% · 86.9% 덮임

**아무 뜻 없는 바이트도 86% 를 덮는다.** 그 위의 92.7% 는 6%p 짜리 이야기다.
「100%」는 **여유가 없다는 뜻이 아니라 자가 포화됐다는 뜻**이었고,
그 판정을 근거로 다른 방에 「그 길은 닫혔다」고 보낸 결론이 하나 정정됐다.

### 통계로 안 되면 구조로 가라

같은 물음을 **구조**로 다시 물으니 답이 났다. 언어 분기가 데이터 주소를
즉값으로 물고 있었으므로, 그 즉값을 롬 전체에서 전수로 뽑았다.

    영어 전용 주소 29개 → 롬 전체 즉값 참조 36개
      그중 35개가 언어 분기 직후 400바이트 안 (대부분 정확히 +7 = 갈래 첫 명령)
    무작위 주소 200개 → 참조 0개

**대조군이 0 이다.** 같은 물음, 같은 롬인데 이 자는 포화돼 있지 않다.
그래서 여기서 나온 「참조 없음」은 근거로 쓸 수 있고, 앞의 둘은 못 쓴다.

    우연은 흩어진 일치를 만든다. 정렬된 표와 정확한 즉값은 못 만든다.
    통계가 죽는 자리에서 구조는 산다.

### 딸린 규칙 — 대조군을 도구 «안에» 박아라

이 대조군들은 전부 나중에 따로 만든 것이다. 그래서 **그 도구를 다음에 쓰는 사람은
또 속는다.** 훑는 도구는 자기 배경률을 스스로 출력해야 한다.
「445곳 걸림」이 아니라 **「445곳 걸림 (무작위 배경 340~979)」**이라고 찍혀야 한다.

## ⑤ 「없다」와 「내 자가 그 꼴을 모른다」는 다르다 — 표 훑기의 실례

위와 같은 조사에서, 「그 구역을 가리키는 **포인터 표**가 있나」를 물었다.
표는 우연으로 안 생기니 좋은 물음이었다. 답은 **없음**이었다.

거기서 이렇게 읽었다 — **「표가 없다 → 주소가 코드에 박혀 있거나 계산된다」.**
방향을 하나 정한 것이다. 그런데 **틀렸다. 표는 있었다.**

    내가 찾은 것   24비트 «절대주소»가 간격 3~4 로 늘어선 표
    실제           16비트 «자기 상대» 오프셋 표

    0x033ED7   f0 00 56 01 c1 01 12 02 …
               └ 0x00F0 → 0x033ED7 + 0xF0 = 0x033FC7 = 글 덩이 시작과 정확히 일치
    120항목 240바이트. 가변 길이 문자열 120개를 이 표 하나가 색인한다.

작은 롬에서는 절대주소를 안 쓴다. **자기 위치에서의 오프셋이 짧고 싸다.**
그걸 안 찾아 놓고 「없다」고 한 것이다.

**「안 나왔다」를 결론으로 쓰기 전에, 내 자가 어떤 꼴만 볼 수 있는지 적어라.**
적어 보면 대개 빠진 꼴이 보인다. 표를 뒤진다면 최소한 이 넷이다.

    24비트 절대 · 32비트 절대 · 16비트 자기상대 · 16비트 다른 밑자리 상대

이건 ①②③ 과 같은 뿌리다 — **검사가 무엇을 못 보는지를 검사하지 않은 것.**
다만 앞의 셋은 「검사가 반응을 못 한다」였고, 이건 **「검사가 애초에 그 모양을 모른다」**다.
전자는 양성 대조로 잡히지만 **후자는 양성 대조로도 안 잡힌다** — 내가 아는 꼴로만
대조군을 만들기 때문이다. 그래서 이건 대조군이 아니라 **목록으로** 막아야 한다.

### 그리고 자기 주장을 깎는 검사라야 믿을 만하다

이 조사의 1차 결론은 「12,459 바이트가 통째로 죽었다」였다.
구조로 다시 재니 **일본어 갈래와 언어에 무관한 코드가 그 안을 가리키고 있었고**,
살아 있는 기록 2개 370바이트를 빼야 했다.

**새 방법이 옛 결론을 «키우기만» 한다면 그 방법을 의심하라.**
제대로 된 자는 자기가 딛고 선 주장도 깎는다.

### ⑤ 에 붙이는 것 — 같은 뿌리의 사례 넷 (2026-09-05)

⑤ 는 「내 자가 그 꼴을 모른다」였다. 하루 더 해 보니 **얼굴이 넷**이다.

**1. 내 자가 그 꼴을 모른다** (원래 ⑤)

    포인터 표를 24비트 절대형으로만 뒤지고 「표 없음」이라 닫았다.
    실제는 16비트 «자기 상대» 오프셋 표였다.

**2. 내 자가 그 «방향»을 모른다**

    램 주소를 무는 자리를 `F2`(메모리 오퍼랜드)로 훑었더니 세 곳뿐이고 전부 «쓰기»였다.
    「이 게임은 언어로 갈래를 안 가른다」는 답이 나올 뻔했다.
    **F2 는 쓰기, C2 가 읽기다.** C2 로 훑으니 71곳·91곳이 나왔다.
    다른 방에서도 같은 날 같은 걸 밟았다 — 4바이트 즉값만 훑고
    「이 표를 무는 곳은 여기뿐」이라 닫았는데, 화면은 표가 아니라 글 바이트를 직접 물고 있었다.

**3. 이미 있는 물건을 안 보고 도구부터 만들었다**

    카드 화면을 열려고 세이브 플래시를 손으로 채우는 수법을 만들었다.
    **그 게임의 «올카드판 IPS» 가 이미 레포에 있었다.**
    도구가 나쁜 게 아니라 **순서가 틀렸다.** 만들기 전에 있는 것부터 봐라.
    (그 수법 자체는 올카드판이 없는 게임에 그대로 쓴다 — 버리는 게 아니다.)

**4. ★ 범위가 안 적힌 «참인» 문장에 속았다**

    문서에 「대사 폰트는 256칸이 이미 꽉 차 있다」고 적혀 있었다. **참인 문장이다.**
    그런데 «어디에» 걸리는지가 안 적혀 있었다.
    나는 그 범위를 「대사 코드 경로」로 짚었는데, 실제 범위는 **VRAM 512타일**이었다.
    같은 롬의 카드 설명은 문장마다 지역 코드를 써서 그 벽이 «아예 없었다».

    **틀린 문장은 부딪히면 깨진다. 범위가 안 적힌 참인 문장은 안 깨지고 사람을 다른 데로 보낸다.**

    → 문서 문장을 근거로 쓸 때는 **그 문장이 «어느 경로에» 걸리는지**를 스스로 확인해라.
      「참이냐」가 아니라 **「내 경우에도 참이냐」**를 물어야 한다.

    같은 날 다른 방에서 짝이 되는 사례가 나왔다 —
    **진단이 틀렸다는 것과 증상이 없다는 것은 다르다.**
    검수자의 원인 진단이 틀렸는데 그 자리에 진짜 증상은 있었다.
    진단을 깨고 「문제 없음」으로 닫으면 증상을 놓친다.

**5. 비율 문턱은 구두점에서 새고, 디코드는 안 샌다** (2026-09-05, 1-f7)

    같은 포인터 배열에 «한글 줄»과 «영어 줄»이 섞여 있었다.
    영어를 「바이트의 80% 이상이 알파벳(≤0x19)이면 영어」로 갈랐더니,
    구두점(0x8F·0x8A…)이 낀 영어 줄 24개가 문턱에 못 미쳐 «한글»로 샜다.
    그걸 「한패가 넣었는데 안 나오는 한글 24줄 = 결함」이라고 적을 뻔했다.

    영어 자(A=0x00…)로 «디코드»하니 "HAH. HAH. HAH. EAT FLAME. FOOL…" — 그냥 영어였다.

**규칙:** 인코딩이 둘 이상 섞인 곳에서 «비율 문턱»으로 가르지 마라.
**각 인코딩으로 디코드해서 «읽히는 쪽»**으로 갈라라. 읽히는지는 눈이 판단한다.

이 한 번으로 줄 수가 56 → 100 → 78 로 세 번 바뀌었다(제어 바이트를 글리프 아님으로 · 구두점 낀 영어를 한글로 · 바로잡음).
세 번 다 「자가 무엇을 못 보는지」를 검사 안 한 것이다.
**결함이라 부르기 전에 그 줄을 «읽어» 봐라. 읽으면 10초, 안 읽고 보내면 물리는 데 하루다.**

### 딸린 규칙 — 손으로 하는 변환은 도구로 막아라

같은 뺄셈(CPU 주소 − 0x200000 = 파일 오프셋)을 **하루에 두 번** 틀렸다.

    0x2319EB → 0x0119EB (틀림, 정답 0x0319EB)
    0x22F11E → 0x00F11E (틀림, 정답 0x02F11E)

두 번 다 «엉뚱한 코드»가 나왔고, 그걸 「구조가 이상하다」로 읽으며 한참 헤맸다.
**틀린 주소는 «없는 것»처럼 보이지 않고 «다른 것»으로 보인다.** 그래서 안 걸린다.
한 줄짜리 변환기를 만들어 두고 손으로 빼지 마라.

## ⑥ 무대의 정체성은 «옵션»이 아니라 «진입 경로»에 있다

같은 날 두 방에서, 서로 다른 모양으로 같은 병이 나왔다.

### 사례 1 — 세이브가 기능을 물고 있었다

한 방은 세이브스테이트에서 무대를 열었다. 화면이 **288×184** 로 나왔는데
다른 방은 같은 코어로 **160×152** 였다. 옵션을 여섯 개 꺼도 안 바뀌었다.

    ngp_ss2sp · comm · comm_draw · comm_duo · comm_spk · sides 전부 disabled
    → 그래도 288×184 그대로

**세이브를 구울 때 켜져 있던 기능이 화면 크기까지 물고 굳어 버린 것**이다.
나중에 옵션을 맞추는 것으로는 못 맞춘다. 그 위에 코어가 그리는 해설 띠가 얹혀
**롬과 무관하게 늘 같은 영역**이 생겼고, 그게 화면 대조를 오염시킬 뻔했다.

    → 화면 대조는 «처음부터 같은 옵션으로 구운» 상태끼리만 해야 한다.
      **화면 크기가 다르면 이미 다른 조건이다.** 그게 제일 싼 검사다.

### 사례 2 — 검증된 대조군이 무대를 옮기니 죽었다

다른 방은 「그 자리에 무한루프를 박아 굳는지 본다」는 자를 썼고,
양성 대조로 **부팅 스텁**에 루프를 박았다. **전에 검증한 자리다. 그런데 안 굳었다.**
세이브스테이트로 들어오면 **부팅 스텁을 아예 안 지나기 때문**이다.

그대로 갔으면 「탐지자가 죽었다」고 잘못 접었을 것이다.
그 무대에서 실제로 도는 자리(언어 분기 전부)로 바꾸니 바로 굳었다.

    → 대조군은 «자리»가 아니라 «그 무대에서 실제로 도는 자리»여야 한다.

**그 자리는 게임마다도 다르다.** 위의 부팅 스텁은 사실 다른 두 게임의 꼴이었고,
이 게임엔 그 스텁 자체가 없다. **검증된 대조군을 게임 너머로 들고 온 것**이었다.

### 사례 3 — 판정 기준도 무대에 딸려 있다

같은 자를 부팅 무대에 옮기면서 판정을 「서로 다른 화면이 2종 이하면 굳은 것」으로 뒀다.
부팅 무대는 **앞부분이 변하는 게 정상**이라 이 자로는 못 잰다. 실제로 대조군을
「안 걸렸다」로 읽었다. **「꼬리 10칸이 한 종인가」**로 바꾸니 바로 잡혔다.

    → 대조군은 «자리»만이 아니라 «그 무대에 맞는 판정 기준»까지 같이 골라야 한다.

### 딸린 규칙 셋

    · 검증했다는 이유로 대조군을 «재검증 없이» 재사용하지 마라.
      무대·진입 경로·게임 중 하나만 바뀌어도 다시 골라야 한다.
    · 무대가 «조용한지» 먼저 재라. 같은 롬을 두 번 돌려 26칸 중 19칸이 달라지는
      무대에서는 그 뒤로 아무것도 못 잰다. 조용한 칸을 골라 그 안에서만 비교하라.
    · **코어와 빌드를 결과에 적어라.** 같은 한글패치라도 빌드가 갈리면 결론이 갈린다.
      실제로 한 게임에서 언어 잠금이 b3 에 «7개», b4 에 «120개» 였다.
      md5 를 안 적으면 그 보고서는 어느 물건에 대한 것인지 모른다.

### 그리고 오늘 셋이 공통으로 밟은 것

**규칙은 남에게 주기 쉽고 자기에게 돌리기 어렵다.**
④를 써서 다른 방에 보낸 사람이 정작 자기 1차 검사엔 안 돌렸고,
그 규칙을 받은 방도 자기 무대엔 안 돌렸다. 셋 다 남이 물어봐 준 뒤에야 돌렸다.

    새 규칙을 적었으면, 그날 «자기가 낸 결론부터» 그 규칙으로 훑어라.
## ⑦ 「탐지자가 산다」와 「무대가 목적지에 닿았다」는 다른 대조군이다 (본부, 2026-09-04)

검사가 **조용하고**(잡음 0) **반응하는데도**(양성 대조 걸림) 답이 틀릴 수 있다.
**그 화면에 안 갔기 때문**이다. 양성 대조는 「코드가 돈다」를 증명하지 「내가 거기 있다」를
증명하지 않는다 — 차림표 코드만 돌아도 대부분의 양성 대조는 걸린다.

### 하루에 다섯 번 밟았다 (전부 「차이 0」을 냈고 전부 「안 가 봤음」이었다)

| 무대 | 결과 | 실제 |
|---|---|---|
| SS2 부팅 60프레임 간격 26칸 | 한패 vs 순정 0/26 | 글자 없는 화면만 지났다 |
| SS2 「기술 설명」 | 0/16 | 커서가 안 움직여 제목 차림표에 머물렀다 |
| SS2 순정 코어 20칸 | 0/20 (잡음도 0) | 어트랙트만 지났다 |
| SS2 COLLECTION | 0/12 | 차림표까지만 갔다 |
| 〃 (추가작업) | 「안 굳었다」 | **카드가 0장이라 게임이 거절**했다 |

마지막이 특히 고약하다 — 버튼이 안 먹은 게 아니라 **게임이 조건 미달로 거절**한 것이라
화면은 멀쩡히 그려지고 대본도 정상으로 돈다.

### 잣대: 「칸별 해시가 실제로 넘어갔는가」

    ① 무대가 조용한가        같은 롬·같은 대본 두 번 → 다른 칸 0
    ② 탐지자가 사는가        일부러 망가뜨린 판에서 걸리는가
    ③ ★ 무대가 닿았는가      칸별 해시가 «서로 다른 그림»으로 넘어가는가

③ 이 빠지면 ①②를 아무리 잘해도 답이 안 난다. 실제로 이 건은 ③ 을 8차에 박고 나서야
답이 났다 — **표적재 루프가 굳고, 화면의 카드 설명문이 표 항목 #0 과 글자까지 같았다.**
(연달아 같은 해시가 나오면 커서만 돌았거나 게임이 거절한 것이다. 넘어간 척하는 화면을 세지 마라.)

### 딸린 것 — 코어가 바뀌면 버튼도 바뀐다

같은 게임인데 **우리 코어는 확인이 `Y`, 원조 메드나펜은 `B`** 였다. 무대 하나가 통째로
헛돌았고 「0/16」의 원인이 그것이었다. **코어를 바꿨으면 버튼부터 다시 확인하라.**
같은 자리에서 화면 크기도 바뀐다 — 우리 코어 288×184 (해설 띠+기둥) / 원조 160×152.
**화면 크기가 다르면 이미 다른 조건이다.** 그게 제일 싼 검사다.

## ⑧ 같은 규칙을 두 군데 적으면 «반드시» 갈라진다 (카드 파이터즈 2편, 2026-09-05)

**있지도 않은 한자 79종을 세고 있었다.** 404종인 줄 알았는데 참값은 325종이다.

### 무엇이 갈렸나

2편은 글 안에 «매개변수를 먹는 코드»가 있다.

    0x01~0x07   앞바이트 — 뒤 한 바이트와 묶여 16비트 색인(한자)
    0x08        말하는 이 — 뒤 한 바이트를 «값»으로 집어삼킨다

글을 걷는 코드가 두 군데 있었다.

    end(rom, o)   글 끝을 찾는다   → 0x01~0x07 «과» 0x08 을 건너뛴다   ○
    dec(b)        읽을 꼴로 바꾼다 → 0x01~0x07 만 건너뛴다              ✗

`dec` 는 0x08 의 매개변수를 «그냥 글자로» 읽었다. 그래서 매개변수가 0x02 이고
다음이 0x79('は') 면 그 둘을 묶어 «색인 0x279 짜리 한자» 로 만들어 냈다.

    ⟨08⟩⟨02⟩は ぁい!   →   ⟨08⟩⟪279⟫ぁい!      ← 없는 한자가 생긴다

한자 표를 만들려고 쓰임새를 훑는데, 그 «없는 한자» 들이 목록 위쪽에 섞여 있었다.
「⟪279⟫ぁい!」 같은 문장을 놓고 「이 한자는 뭘까」를 한참 궁리했다. 답이 없는
물음을 붙들고 있었던 것이다.

### 왜 안 보였나 — 두 쪽 다 «틀린 채로 일관»되게 돌았다

`end` 는 맞고 `dec` 는 틀렸는데, 둘이 같은 글을 놓고 서로 다른 답을 내도
**아무 데서도 안 부딪힌다.** 끝 자리는 맞으니 글이 안 잘리고, 읽은 꼴은
사람이 보기 전엔 아무도 안 센다. 어긋남이 «화면»이나 «assert» 로 안 나온다.

그래서 이 병은 오래 산다. 오늘 같은 모양이 세 곳에서 따로 나왔다.

    카드 파이터즈  end 와 dec 에 따로 적은 「매개변수 건너뛰기」
    이식소        다이얼 표를 두 군데로 알고 있다가 빠진 칸을 물려받음
    본부          인풋 패치가 어느 레포로 나가는지를 두 군데로 알고 있었음

### 고침 — 규칙을 «한 군데»에 두고 나머지는 그것을 부른다

    def codes(b):
        """글을 «게임이 걷는 대로» 걸으며 (자리, 코드) 를 낸다."""
        i = 0
        while i < len(b):
            c = b[i]
            if 1 <= c <= 7 and i + 1 < len(b):
                yield i, (c << 8) | b[i + 1]
                i += 2
            elif c == 0x08 and i + 1 < len(b):
                i += 2                      # 매개변수는 글자가 아니다
            else:
                yield i, c
                i += 1

세는 쪽(`cf2_kmap.used`), 읽는 쪽(`dec`), 고르는 쪽(`cf2_kid.scan`) 을 전부
이것으로 돌렸다. 그 자리에서 404 → 325 로 떨어졌다.

### 잣대

    · 「걷는 규칙」이 두 파일에 적혀 있으면 그 자체가 결함이다. 아직 안 갈렸을 뿐이다
    · 두 쪽이 낸 답을 «서로» 대 봐라 — 각자 그럴듯하면 둘 다 안 걸린다
    · 종수·개수처럼 «세어 나온 숫자» 는 세는 규칙이 하나인지부터 보라.
      숫자가 틀리면 그 위에 쌓은 판단이 전부 틀린다. 나는 이 79종 위에서
      「긴 꼬리라 표 만들기가 힘들다」고 잘못 셈했다

### 딸린 것 — 「0곳」은 «분모»와 같이 말해야 뜻이 있다

같은 날 두 칸 목록 검사기를 만들었더니 「어긋난 곳 0」이 나왔다. 좋아 보였는데
조건이 좁아 **두 곳밖에 안 봤다.** 조건을 넓히니 34곳을 보고 7곳이 어긋나 있었다.

    print('두 칸 목록 %d곳 가운데 어긋난 곳 %d' % (len(seen), len(bad)))

**분모를 안 찍는 검사는 «0» 이 무슨 뜻인지 말해 주지 않는다.**
